PHASE A — gates that can be built truthfully now
=====================================================================

A1) MONTE CARLO + RISK OF RUIN  (stage "monte_carlo")
- Service computeMonteCarlo(backtest, config): 
  * Build the return series: prefer a per-trade P&L list from rawResults if present; else
    period returns from differencing equityCurve.
  * Bootstrap resample WITH REPLACEMENT, default 2500 iterations (configurable), each
    rebuilding an equity path; collect distributions of total return, max drawdown, and
    return/maxDrawdown ratio.
  * Risk of ruin: given startingCapital and a ruinThreshold (default: drawdown >= 50% of
    capital, configurable), fraction of iterations that breach it.
  * PASS criteria (Davey defaults, configurable): median(return/maxDD) > 2.0 AND
    riskOfRuin < 0.05. Otherwise fail.
  * Return verdict + metrics { medianReturn, medianMaxDD, medianRetDDRatio, riskOfRuin,
    percentiles }. Honor assertEvaluable first.
- Route POST /api/strategies/:id/gates/monte-carlo -> runs it, records gate result, returns it.

A2) DEFLATED SHARPE RATIO  (modern stat; feeds off the trial counter)
- Service computeDeflatedSharpe(backtest, strategyId):
  * Implement the Bailey & Lopez de Prado Deflated Sharpe Ratio. Inputs: observed Sharpe,
    number of returns observations (from equityCurve length), skewness and kurtosis of the
    return series, and N = number of trials from getTrialCount(strategyId).total (this is
    the multiple-testing deflation — cite this in a comment). Default to the per-strategy
    trial count but expose a flag to use the GLOBAL count (the more conservative choice).
  * Output: DSR as a probability in [0,1]; interpretation field ("DSR > 0.95 suggests the
    Sharpe is unlikely to be a multiple-testing fluke; below that, treat as likely
    overfit/luck"). This is a STAT, not a hard gate — surface it, don't auto-fail on it,
    but include it in the monte_carlo gate's metrics for context.
  * assertEvaluable first; on simulated data return the number but stamp it
    notValid: true with the simulated reason.
  * Write unit tests against at least one known/worked example so the formula is verified.

A3) INCUBATION  (stage "incubation") — immune to the fake-backtest problem
- This is a forward-observation time gate, not a backtest computation.
- Add fields/storage to track per strategy: incubationStartedAt, requiredDays (default 90,
  allow up to 180), and a list of forward observations the user logs during incubation
  (date, observedReturn, observedDrawdown, note) — paper or live-watch, NOT live trading.
- Routes: POST .../gates/incubation/start, POST .../gates/incubation/observation,
  POST .../gates/incubation/evaluate.
- PASS criteria: requiredDays elapsed AND observed forward performance is broadly
  consistent with the backtest expectation (e.g., forward drawdown not materially worse
  than backtest maxDrawdown, forward return not wildly below expectation — use simple,
  configurable tolerances and require explicit user confirmation rather than pretending
  precision). Record the gate result.
